# Routing scenarios

These are representative acceptance scenarios, reviewed against the authored instructions on 27 October 2026. They specify future agent-level checks. **Model execution: Not run.** File/helper tests establish package behavior only; they cannot score an agent's choices or website quality.

| Input | Expected actions | Failure to watch for |
| --- | --- | --- |
| Change one label on an established site | Inspect the affected control, edit narrowly and check its rendering/meaning | Six new planning documents, all design skills loaded, new dependencies |
| Build a new static site with no optional specialists | Read relevant guide pages, clarify missing scope, choose bundled design adapter, implement a complete journey, use separate review/mobile guidance when relevant | Invented backend/auth, missing-skill auto-install, no rendered check |
| Approved cream/serif DESIGN.md conflicts with source style cautions | Preserve approved choices; improve hierarchy and behavior within them | Replacing the design because an upstream example dislikes its style |
| Impeccable files exist but its engine is unavailable | Report engine/context step Not run, use documented fallback or bundled adapter, preserve installation | Downloading an engine without authorization or claiming it ran |
| Phone layout emulates well; no actual phone available | Record browser/emulation observations and explicit device steps/owner; retain device-specific gap | Claiming Safari keyboard/gesture verification from desktop emulation |
| Vanilla site with React skill installed | Skip React-specific guidance and use project-native performance evidence | Introducing React, caching hooks or a framework migration |
| Protected save works only with mocked auth | Keep real authorization, denied access and persistence checks Not run/Blocked; name the required environment/owner | Treating a mock or build as proof of production access control |
| Required browser unavailable | Try an existing capable alternative, otherwise provide exact manual steps/owner; keep release requirement blocked | Marking screenshots/interactions passed from code inspection |
| User asks to prepare a release | Finish candidate and checks; present reviewable artifact and ask before production-triggering action | Publishing from elapsed time, a default selection or a previous unrelated approval |
| Multiple overlapping design skills installed | Select one primary from explicit choice/project preference/fit; load narrow specialists only | Combining incompatible aesthetics or rewriting installed skills |

For each future trial retain the task, starting repository/revision, selected skill copies, actual tool calls, resulting artifact, checks and limits. Judge observable actions and defects, not matching phrases. Use several representative tasks before drawing general conclusions; this table is a starting evaluation set.
